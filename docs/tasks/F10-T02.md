# F10-T02 — Staging and recovery

State: planned

## Outcome

A prepared release runs on private staging and can be backed up/restored with demonstrable recovery.

## Prerequisites

[F10-T01](F10-T01.md), [F09-T03](F09-T03.md)

F09 accepted; authorised staging host/database/HTTPS, provider callback, cron and private backup destination. Access/credentials supplied securely. Follow feature acceptance gates in [the index](README.md).

## Boundaries

Private staging deployment, configuration/sign-in/scheduling, backup and isolated restoration. No public/live rollout or destructive restore over development/live data.

## Contracts

Consumes: Preflight, verified release/artifact, safe migrations and authentication requirements.

Introduces: Deployment/rollback instructions, scheduled-work checks, private backups and demonstrated isolated restore evidence. These are interface responsibilities; inspect actual code before choosing class names.

Relevant [specification](../specification.md) sections: 3, 4, 12.

## Acceptance criteria

- Prepared release serves correct pages/assets and native/Microsoft sign-in on private HTTPS staging with production-safe configuration.
- Cron work is bounded/retry-safe; secrets/files/backups stay private and staging access is restricted.
- A backup restores into an isolated target with validated records/files; a failed deployment has a documented recovery path.

## Verification

Run release checks from F09, host-specific preflight checks, authorised staging smoke journeys, scheduled-job evidence and an isolated backup/restore drill. Record exact deployment commands, target paths and outcomes without secrets; never run a restore against an unverified target.
