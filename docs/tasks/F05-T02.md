# F05-T02 — Submission and HR review

State: verified

## Outcome

Submission freezes a review revision; HR reviews or returns it with reasons and preserves resubmission history.

## Prerequisites

[F05-T01](F05-T01.md), [F04-T02](F04-T02.md)

HR completeness/evidence rules and return/review responsibilities. Follow feature acceptance gates in [the index](README.md).

## Boundaries

Submit, immutable snapshot, HR review/return and successor drafts. SLT approval and employee release are later tasks.

## Contracts

Consumes: Drafts, framework/calculation, ratings/targets/evidence, participants, pay/benchmarks and operational context.

Introduces: Immutable submission revision, preserved evidence references, HR transitions/reasons and explicit resubmission lineage. These are interface responsibilities; inspect actual code before choosing class names.

### Implementation contract

- Append PdrSubmission with review/draft lineage, monotonically unique submission number, schema version, private JSON snapshot and author/time. Locked drafts and submissions reject mutation/deletion. Review head stores the current submission ID and optimistic version.
- The assigned current manager submits an open-cycle draft using both head and draft tokens. Employee reflection when required, manager summary, at least one fully described/measured/dated objective and a complete reproducible score are mandatory. Snapshot the exact framework, calculator inputs, participant/profile/cycle, assessment revisions/notes, target context, pay/proposal/benchmark/context records. Missing optional files are explicitly marked unavailable; required evidence must be intact. Copy intact evidence to private immutable revision paths and verify hashes before commit; clean uncommitted staged copies on failure.
- Current scoped HR review authority, excluding subject and assigned submitting manager, may mark only the current submitted revision reviewed or return it with a reason. Append transition events; return creates a new draft copied from the locked source, preserving lineage. No old revision is edited.
- Internal snapshot pages are projected server-side using current person and independent actual-pay, benchmark, recommendation and sensitive-context grants. Employees cannot access internal revisions before release. All downloads re-authorise and audit.
- Test stale/duplicate/forged transitions, completeness, source/file changes, immutable copies, return/resubmit lineage and filtered response data on SQLite and isolated MySQL.

Relevant [specification](../specification.md) sections: 5, 9.

## Acceptance criteria

- A complete permitted draft submits once with frozen inputs/context and a reproducible breakdown.
- Missing required evidence, forbidden transitions/actors and stale/duplicate submissions are rejected atomically.
- Later source/framework/file edits cannot alter old revisions; returns preserve prior submissions and create a distinct editable successor.
