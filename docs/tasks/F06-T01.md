# F06-T01 — Development actions

State: verified

## Outcome

Identified gaps/objectives become owned, dated development actions with progress and completion evidence.

## Prerequisites

[F02-T03](F02-T03.md), [F05-T04](F05-T04.md)

F02/F05 accepted before dependent feature work; HR defines employee/manager edit responsibilities. Follow feature acceptance gates in [the index](README.md).

## Boundaries

Skills/review-linked actions and leadership development, course/resource links and progress. No course-management/LMS system.

## Contracts

Consumes: Scoped assessments, review objectives and private-evidence conventions.

Introduces: Development action owner/due/status/progress contract and evidence linked to originating gap/objective. These are interface responsibilities; inspect actual code before choosing class names.

### Implementation contract

1. DevelopmentAction is a stable employee-owned head with immutable DevelopmentRevision rows and optimistic revision token. The subject employee owns every action; current supervisors or scoped HR review administrators create/update plans, and the employee/current supervisors record intended progress. Organisation-view access alone cannot read or assign development plans.
2. Plans carry explicit title/description, start/due dates, optional labelled HTTP/HTTPS resource/course link, and one fixed origin: an applicable skill/optional permitted assessment revision, a released review objective belonging to the same employee, or explicit manual/leadership development. Snapshot a permitted source label and target provenance without copying raw manager assessment comments/ratings, pay or comparisons into employee-facing state. Review origin uses released objectives, so F05-T04 is the actual dependency.
3. Every plan/progress update appends a revision containing plan/status/notes/completion date and previous evidence reference. Status is planned, in_progress, completed or cancelled. Completion requires notes or a validated intact private attachment and a real date between start and today. Cancellation/reopening a terminal action requires current supervisor authority and a reason. Completed/cancelled plans must be reopened before metadata changes.
4. Validate date order, bounded text, explicit resource label and safe HTTP/HTTPS URL without embedded credentials. Completion files use existing private evidence storage, PDF/JPEG/PNG content plus extension validation and 10 MiB limit; record size/digest/name and author. Stage outside retryable transactions and clean only unreferenced files after failure. Every download rechecks scope/integrity and audits.
5. Full-page employee action lists and revision history expose scalar allowlists, resource links and explicit overdue/completion status. Stale forms retain input with their original token until explicit reload. Link permitted assessment/released-objective journeys into the create form. Test intended creation/progress/evidence, scope/forged origins, role/grant/reporting changes, safe links/dates/status, terminal rules, stale recovery and failed-upload cleanup on SQLite/MySQL.

Relevant [specification](../specification.md) sections: 6, 10, 11.

## Acceptance criteria

- Authorised users create/follow actions from a gap or objective and attach completion evidence.
- Users cannot assign/view/update actions outside their scope or fetch another employee's private completion file.
- Invalid dates/status changes, unsafe links and stale updates fail clearly without losing legitimate progress.
