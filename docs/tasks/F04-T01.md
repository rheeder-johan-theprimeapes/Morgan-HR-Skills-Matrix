## Boundaries

## Contracts

Consumes: Employee identifiers and separate pay/benchmark capabilities.

Introduces: Effective-dated actual pay, sourced benchmarks and compatible comparison results with visible conversion assumptions. These are interface responsibilities; inspect actual code before choosing class names.

1. Add immutable PayRecord and PayBenchmark with explicit minor-unit amounts, basis/currency, optional paired hours/weeks, effective/source periods, provenance and correction links. Retain prior entries; use a per-person sequence and correction uniqueness for stale writes. Add useful factories and safe illustrative-only seeders.
2. Centralise explicit amount/assumption validation and comparison formulas; current capability plus people scope protects every actual-pay entry point, while separate benchmark capability protects its library. No automatic defaults, currency exchange, increase recommendation or actual-pay changes from review approval.
3. Write focused HTTP/action tests first for history/effective selection/corrections, conversion/comparability, validation/stale writes and confidential direct-request boundaries. Build full-page history, benchmark and comparison forms.
4. Run isolated SQLite/MySQL, analysis/Pint/build. Continue operational context before the independent F04 feature review.

Relevant [specification](../specification.md) sections: 5, 8.

## Acceptance criteria

- Permitted users maintain annual/hourly records and comparable benchmark evidence with source/dates.
- Employees and actors without the exact pay capability cannot retrieve fields through forms/payloads/direct requests.
- Unknown/incompatible units, missing hours, invalid amounts/dates and stale edits cannot produce a guessed or corrupted comparison.
