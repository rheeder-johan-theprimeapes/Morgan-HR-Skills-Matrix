## Outcome

Authorised HR manages employees, departments, roles, reporting lines and account links.

## Prerequisites

[F01-T01](F01-T01.md)

Synthetic roster for development; stable real employee identifiers/reporting structure needed before live imports. Follow feature acceptance gates in [the index](README.md).

## Boundaries

Directory administration with active/retired records and hierarchy integrity. No general employee-system API integration.

## Contracts

Consumes: Account/person identifiers and restricted provisioning capability.

Introduces: Stable employee key, department/role membership, current reporting tree, reusable descendant resolution and protected references. These are interface responsibilities; inspect actual code before choosing class names.

### Implementation plan

- Extend the existing Employee with optional department_id, job_role_id and manager_id; keep employee_number immutable in ordinary edits. Introduce Department and JobRole with stable unique codes, names and active status. Use restrictive foreign keys and retirement instead of deletion.
- Introduce a distinct can_manage_directory capability while F01-T04 consolidates grants; account administration alone grants no directory or salary access. Synthetic HR fixtures hold the required explicit capabilities. Real grants remain a deliberate console/HR decision, not an inferred role.
- SaveEmployee::handle(User $actor, ?Employee $employee, array $data): Employee authorises directory management, locks the current employee graph in primary-key order inside a transaction, validates the selected active department/job role/manager, rejects self-management and ancestor cycles, then applies the allowed fields. Reassignment and retirement cannot leave active direct reports under a retired manager. Retirement preserves all rows and revokes a linked account.
- ReportingTree::descendantIds(Employee $manager): array returns current direct/indirect descendant IDs with cycle protection. F01-T04 uses this for scope; list screens use stable ordering and pagination.
- HR can explicitly link an intended unlinked account to one employee, with uniqueness and capability checks under locks; no email matching. Provisioning an existing directory person requires the account-administration capability and reuses the person instead of duplicating the stable ID.
- Use thin directory/catalogue controllers, form requests and policies, shared Blade forms and ordinary navigation. Add tests/Feature/OrganisationDirectoryTest.php for authorised saves, validation, graph cycles, retirement, account conflicts and denial. Add bounded generated graph coverage using the existing seeded Eris support.
- Observe focused failures before implementation; run focused tests, Pint, analysis, full fast/MySQL profiles and build. Keep development data unchanged and record exact results.

Ruling: serialise the small current reporting graph while saving HR edits (about 200 people). This avoids concurrent reciprocal-manager writes without adding a lock table; cost if organisation size grows substantially is revisiting write contention.

Relevant [specification](../specification.md) sections: 4, 5.

## Acceptance criteria

- HR creates/updates a person, assigns department/role/manager and links one intended account.
- Duplicate stable IDs, self-management, reporting cycles and conflicting account links are rejected atomically.
- Unauthorised actors cannot edit the directory; retiring a person does not delete history required by reviews.
